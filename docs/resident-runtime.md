# Резидентный runtime и поток PCM

`SynthesisRuntime` загружает RUAccent, TensorRT engines, fixed-prompt state и
CUDA Graph один раз. Перед каждой репликой runtime восстанавливает исходное
состояние `temp_former`, `dep_former` и Mimi. Поэтому запросы не продолжают
KV-state или аудиосостояние предыдущей реплики.

## Python API

`synthesize_stream()` возвращает итератор сырых PCM-чанков. Каждый чанк
содержит 1920 mono-сэмплов `s16le` при 24 кГц: 3840 байт или 80 мс звука.

```python
with SynthesisRuntime(files, ruaccent_assets=accent, phone_map=phones) as tts:
    stream = tts.synthesize_stream("Привет! Я уже говорю по мере генерации.")
    for pcm_s16le in stream:
        audio_sink.write(pcm_s16le)
    metrics = stream.result
```

Если потребителю нужен WAV, `synthesize_to_wav()` записывает те же чанки и не
запускает отдельный путь генерации. Поле `stream.result` заполняется после
полного чтения потока. Незавершённый поток нужно закрыть методом `close()`.

Runtime допускает только одну активную реплику. Это соответствует текущему
сценарию колонки и не прячет очередь внутри TTS.

## Длинный текст

Профиль TensorRT phone encoder принимает от 2 до 640 позиций за один запуск.
Это ограничение одного сегмента, а не всей реплики. Если frontend получает
более длинную последовательность, runtime рекурсивно делит исходный текст:
сначала по границе предложения, затем по запятой или другому знаку и только в
крайнем случае по пробелу.

Все сегменты входят в один `SynthesisStream`: потребитель получает обычную
последовательность PCM-чанков, а resident отправляет один `S`, один `D` и
сколько угодно записей `P`. TensorRT engines и RUAccent не перезагружаются.
Перед каждым сегментом сбрасывается акустическое состояние, поэтому на границе
предложения возможна небольшая смена просодии, но WAV и PCM-поток не
обрываются.

Итоговые метрики содержат `segmented=true`, `segment_count` и массив
`segments`. `max_frames` применяется отдельно к каждому сегменту; значение по
умолчанию увеличено до 1024 кадров. Единственный непреодолимый случай — одна
последовательность без пробелов, которую нельзя безопасно разделить.

## Резидентный процесс

Модуль `voxtream2_ru_jetson.resident` читает из stdin по одному JSON-объекту на
строку. Минимальный запрос:

```json
{"id":"turn-1","text":"Сейчас первый звук придёт без повторной загрузки модели."}
```

Дополнительно можно передать `seed`, `max_frames`, `allow_unknown_phones` и
`include_trajectory`. Процесс обрабатывает запросы последовательно и остаётся
загруженным до закрытия stdin.

Stdout — бинарный поток записей. Заголовок каждой записи занимает 5 байт:

```text
1 byte tag | uint32 little-endian payload length | payload
```

| Tag | Payload | Значение |
| --- | --- | --- |
| `R` | JSON | runtime загружен и готов |
| `S` | JSON | началась новая реплика |
| `P` | raw PCM | очередной `s16le`-чанк |
| `D` | JSON | реплика закончилась, приложены метрики |
| `E` | JSON | запрос завершился ошибкой |

Сам resident резервирует исходный stdout под протокол до загрузки TensorRT, а
последующие native-логи направляет в stderr. Payload больше 16 MiB отклоняется:
так случайный текст в stdout приводит к явной ошибке вместо неограниченного
ожидания ложного бинарного пакета.

При запуске через NVIDIA container всё равно нужно переопределить штатный
entrypoint на `python3`: его приветственный текст появляется до запуска
resident и иначе попадёт в бинарный stdout перед записью `R`.

## Потоковое воспроизведение

`voxtream2-ru-jetson-playback` запускает resident как дочерний процесс и после
`R` отправляет один запрос. Каждый пакет `P` немедленно записывается в stdin
аудиоплеера; клиент не ждёт `D` и не собирает полный WAV. По умолчанию
используется `aplay` с периодом 80 мс и буфером 320 мс:

```bash
voxtream2-ru-jetson-playback \
  --text "Проверяем потоковое воспроизведение." \
  --device hw:2,0 -- \
  voxtream2-ru-jetson-resident <аргументы runtime>
```

Для smoke test без звуковой карты можно передать
`--player-command "dd of=/tmp/stream.pcm bs=3840 status=none"`.

Это локальный транспорт для прототипа, а не сетевой TTS-сервис. Отмена текущей
реплики, параллельные запросы, очередь с приоритетами и восстановление клиента
после разрыва пока не реализованы.

## Проверка на Jetson

В одном процессе дважды сгенерирована одна и та же контрольная реплика с
одинаковым seed. Оба WAV получили SHA-256
`8d4e80b1106ad4e61bedd98c51f48a5aebb778475b63ba5e6bfc1a843e20351c`.
Первый запрос отдал начальный PCM-чанк через 0.425 секунды после получения
текста, второй — через 0.231 секунды. Полная загрузка runtime перед первым
запросом заняла 14.46 секунды.

Отдельная последовательность «длинная реплика → короткая реплика → длинная
реплика» проверила смену динамической длины phone encoder. Первая и третья
реплики снова дали одинаковый контрольный SHA-256, короткая реплика выдала 11
PCM-чанков.

Peak RSS составил 3.50 GiB. Рост относительно одноразового процесса ожидаем:
RUAccent теперь остаётся загруженным рядом с TensorRT engines. Это нужно
учитывать при совместном запуске TTS и STT на Jetson 8 GB.

Единый q=1/q=420 plan проверен тем же транспортом: 75 чанков были переданы в
raw PCM sink во время генерации, а итоговый размер `288000` байт точно совпал с
`75 × 3840`. Первый чанк появился через 0.417 секунды после запроса; генерация
шестисекундной реплики заняла 5.268 секунды. Физическая USB-колонка в этом тесте
не была подключена.
